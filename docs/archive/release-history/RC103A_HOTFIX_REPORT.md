# RC103A Hotfix Report

## 1. Hotfix Summary
In response to the critical recall regressions observed in the Vul4J and GitHub datasets, we executed a **Partial Rollback** of the `RC103` hardening changes. Specifically, we completely reverted the **Source Seeding Refinement** logic from the engine's interprocedural entrypoint discovery phase while preserving the highly-effective **Sink Argument Gating** (CWE-502).

## 2. Code Reverted
The overly restrictive entrypoint filter in `crates/taint/src/interproc.rs` (lines 409-418) was removed.

**Removed Logic (RC103):**
```rust
            if !has_caller {
                let is_constructor = method.name == "__init__" || method.name == "<init>";
                let is_private = method.name.starts_with('_') && !method.name.starts_with("__");
                if is_constructor && total_callers == 0 {
                    // Do not seed constructor if the class has zero instantiations anywhere in the codebase
                } else if is_private {
                    // Source Seeding Refinement: Do not automatically treat uncalled private methods as entry points.
                    // This prevents FPs where internal helper functions are flooded with generic taint.
                } else {
                    is_entry = true;
                }
            }
```

**Restored Logic (RC103A Baseline):**
```rust
            if !has_caller {
                is_entry = true;
            }
```

## 3. Expected Impact

*   **TP Recovery (Recall):**
    *   **Vul4J**: We expect a **100% recovery** of the 12 Vul4J True Positives. The engine will once again properly seed `PathResolver.resolve`, `Render.welcome`, and other public wrapper methods that evaluate to `!has_caller` due to being called purely by ignored test frameworks.
    *   **GitHub/OWASP**: We expect the immediate recovery of the ~15-20 TPs (e.g., PaddlePaddle's `_wget_download` CWE-78 and GitPython `_` helper methods) that were incorrectly banned by the `is_private` check.
    *   Combined Recall will return to the `~85.00%` baseline established in RC101A.

*   **FP Impact (Precision):**
    *   The False Positives generated by uncalled constructors and internal helper wrappers will return. However, because we **preserved** the Sink Argument Gating logic, we expect GitHub Precision to remain noticeably elevated compared to the pre-RC103 baseline (stabilizing around `~58.00%` up from `56.60%`).

## 4. Risks & Next Steps
*   **Risk:** The baseline behavior is slightly noisy because it floods internal python methods and Java constructors with generic taint. This noise will need to be addressed later with a more contextual tracking approach rather than a blunt `name.starts_with('_')` filter.
*   **Next Steps:** Validate RC103A via the `v2-validation` harness to confirm exact metric recovery, and then proceed directly to the `RC104 MULTI_FILE_IMPORT` roadmap to address the remaining cross-file resolution gaps.
